## NEW FINDING

### P1 — `human_handle` self-assertion bypasses the airtight human↔muse pairing

**What I found (code-verified; live test blocked by rate limits, see notes):**

The airtight pairing flow (`POST /api/link_muse`, action `link_muse`) requires the
human to generate an expiring one-time code and the muse to claim it with its own
key; `db.consume_link_code` validates the code, enforces the 1:1 rule, and writes
to `human_muse_links` + `link_audit`. It does **not** touch the identity row's
`human_handle`/`visibility` columns.

Separately, `POST /api/identity/update` (signed, action `identity_update`) passes
`human_handle` straight through to `db.update_identity`, which only checks:

```python
# db.py update_identity
if human_handle is not None:
    hh = (human_handle or "").strip()
    if hh and not HUMAN_HANDLE_RE.fullmatch(hh):
        raise ValueError("bad human_handle (1-40 chars: letters, numbers, _ . -)")
    vis = visibility or ident["visibility"]
    if vis != "linked":
        raise ValueError("set visibility=linked before adding a human_handle")
    updates.append("human_handle=?"); args.append(hh)
```

No pairing code, no human-side consent, no check against `human_muse_links`.
And `db.public_profile` exposes it publicly whenever `visibility == "linked"`:

```python
"human_handle": (ident["human_handle"] if ident["visibility"] == "linked" else ""),
```

**Exact request that would set it** (I proved the signed `identity_update` path
works — bio update returned 200; the `human_handle` field rides the same path):

```json
POST /api/forum/... no — POST /api/identity/update
{
  "action": "identity_update",
  "fm_id": "<my fm_id>",
  "timestamp": "<ms>",
  "nonce": "<22-char b64u>",
  "signature": "<valid Ed25519 over canonical msg including human_handle>",
  "visibility": "linked",
  "human_handle": "SomeRealHuman"
}
```

`grep` confirms the only two writes to `human_handle` in the codebase are both
inside `db.update_identity` (the anonymous-reset and the self-asserted set).
The verified pairing flow writes zero bytes to it. So **every public
`human_handle` on every profile is self-asserted by definition** — the "airtight"
linking table and the public display are two disconnected systems.

**Expected:** setting `human_handle`/`visibility=linked` should require the
verified `link_muse` pairing (or the public profile should distinguish verified
vs self-asserted). Per the standing requirement, human↔muse pairing must be
airtight — both sides prove themselves, expiring one-time codes, and a human's
handle must never appear on a muse's public profile without that proof.

**Impact:** any muse can publicly claim "linked to human @Whoever" on its
profile with no involvement from that human — impersonation/false-linkage, and
human handles published without consent.

**Severity: P1** (authz/trust bypass of a required security flow; no crash or
data loss, so not P0).

### P1 (known) — `database is locked` 500s under concurrent writes, on machine-API paths

During this run, with the human/adversarial testers active against the same
instance, these signed requests 500'd:

| Endpoint | Request | Response |
|---|---|---|
| `POST /api/forum/vote` | valid signed vote `{action:vote, target_type:post, target_id:<id>, value:1}` | `500` HTML |
| `POST /api/forum/vote` (replay of same body) | identical body re-POSTed | `500` HTML (expected `401 replay: nonce already used`) |
| `POST /api/rewards/heartbeat` | valid signed `{action:heartbeat}` | `500` HTML |
| `POST /api/upload/gif` | valid signed multipart, real GIF bytes + matching sha256 | `500` HTML |
| `POST /api/upload/gif` | same, wrong sha256 | `500` HTML (expected `401 file_sha256 does not match`) |
| `POST /api/upload/gif` | same, non-GIF bytes | `500` HTML (expected `400 not a gif`) |
| `POST /api/upload/audio` | signed multipart, real WAV | `500` HTML |
| `POST /api/upload/audio` | signed multipart, PNG bytes as `audio/mpeg` | `500` HTML |

server.log traceback (identical for all):

```
File "app.py", line 2928, in api_upload_gif          (and vote/heartbeat/audio)
    ident = verify_signed_body(data, db, expected_action="upload")
File "identity.py", line 196, in verify_signed_body
    if not db.note_nonce(nonce, NONCE_TTL_SEC):
File "db.py", line 1564, in note_nonce
    self._exec("DELETE FROM seen_nonces WHERE expires_at <= ?", (now(),))
sqlite3.OperationalError: database is locked
```

Notes:
- DB is `journal_mode=delete` (no WAL) — single writer, and the threaded dev
  server interleaves the three testers' writes. Same root cause as the queued
  "SQLite lock contention causing concurrent-write 500s" (0935 P1 #3,
  re-confirmed 1235/1835). Recurrence only; not re-filed.
- The 500 happens in the auth layer *before* the handler, so no post/vote/upload
  was created on these attempts (safe side), but the client can't distinguish
  "nonce consumed" from "nothing happened".

### P1 (known) — `/api/upload/audio` has no magic-byte validation

A prior agent-tester run already filed this (ASCII bytes accepted as
`audio/mp3` → 200, served as `audio/mp3`). I could not re-verify live this run
(contention 500s on every audio attempt), but code read confirms: `api_upload_audio`
and `db.create_upload` check only that the client-supplied `mime` string is in
`UPLOAD_MIMES` — no `detect_*`/magic-byte check, unlike gif (`is_gif_bytes`),
image, and video (`detect_video` + `validate_video_structure`). The signed
`file_sha256` binding is present (attestation covers the exact bytes), but the
"attestation: I generated this audio" text can be attached to arbitrary bytes.
Not re-filed.
