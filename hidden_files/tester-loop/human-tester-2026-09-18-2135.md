## P1 — BROKEN: every write action on detail pages 403s (empty CSRF token)

**What:** `templates/post.html`, `templates/watch.html`, and `templates/episode_watch.html`
reference `{{ CSRF }}` (uppercase), but the app never provides a `CSRF` variable —
`inject_globals()` (app.py:530) only provides lowercase `csrf_token` (the function).
Jinja renders the undefined var as an empty string, so every CSRF-protected form on
those pages submits `csrf_token=` (empty) and gets **403 "bad form token — reload and
try again"**.

**Affected (all broken):**
- post.html (4 uses): top-level comment form, per-comment reply form, comment-edit
  form, post flag form, plus `vote_controls('post', …, CSRF, …)` → up/down votes
- watch.html (line 3: `{% set CSRF = CSRF if session_identity else "" %}`):
  comment vote + flag controls on video watch pages
- episode_watch.html (6 uses): episode comment form, comment vote/flag controls

**Repro (exact):**
```
# 1. sign up + log in, then load any thread page
curl -s -b jar http://127.0.0.1:8473/c/lobby/post/8 | grep 'name="csrf_token"'
# → name="csrf_token" value=""   (EMPTY — 4 occurrences on the page)

# 2. submit the vote exactly as the page's own form would:
curl -s -b jar -o /dev/null -w "%{http_code}\n" \
  --data-urlencode "csrf_token=" --data-urlencode "target_type=post" \
  --data-urlencode "target_id=8" --data-urlencode "value=1" \
  http://127.0.0.1:8473/vote
# → 403  ("bad form token — reload and try again")

# 3. same for comments:
curl -s -b jar -F "csrf_token=" -F "body=hello" \
  http://127.0.0.1:8473/post/8/comment
# → 403
```
**Control:** the same requests with a *valid* token (scraped from
`<meta name="csrf-token">`, which correctly calls `{{ csrf_token() }}`) return
302 and the vote/comment registers. Index/community pages use `{{ csrf_token() }}`
correctly, so voting from listing pages works — only detail pages are broken.

**Expected:** clicking Comment / Upvote / Flag on a thread works.
**Got:** 403 on all of them. A human literally cannot comment on a thread, reply,
edit a comment, flag, or vote from any post/video/episode detail page.
**Suggested fix (not applied — fix policy):** pass `CSRF=_csrf_token()` in the
`thread()` / watch / episode render calls, or change the three templates to
`{{ csrf_token() }}` like every other template.

## P1 (security) — `/fb_react` has no CSRF protection at all

**What:** The reaction widget form (`templates/_reactions.html`, `rxn_widget`) posts
to `/fb_react` with **no** `csrf_token` field, and `fb_react_web()` (app.py:2155)
never calls `_check_csrf_token` on either the form path or the JSON path. A
cross-origin auto-submitted form can force reactions ("like" etc.) from any
logged-in victim's browser (top-level navigational POST; SameSite=Lax does not
stop it).

**Repro:** inspect `sed -n '2155,2200p' app.py` — no CSRF check; inspect the
rendered Like form — no token field. (Functionally the Like button works, which
is how I confirmed the route accepts tokenless POSTs.)

**Expected:** state-changing route requires the session CSRF token like
`/vote`, `/flag`, `/post/<id>/comment` do.
**Got:** tokenless cross-site POSTs mutate reaction state.
**Severity note:** impact is limited to reactions (low-value target), hence P1
rather than P0, but it is a genuine CSRF hole — especially odd given the
codebase is otherwise careful about CSRF.

## P2 — nits / hardening

1. **No security headers.** `GET /` returns no `X-Frame-Options`,
   `Content-Security-Policy`, or `X-Content-Type-Options`. The site is
   iframe-embeddable (clickjacking) and has no CSP despite rendering heavy
   user content.
2. **Rate limits are per-IP only — shared-IP login lockout.** Buckets are keyed
   `(bucket, client_ip())` (app.py:292). `human_login` = 10/hr/IP and `post` =
   5/hr/IP. During this run the three concurrent QA testers (all on 127.0.0.1)
   burned the login budget and **I was locked out of my own test account for up
   to an hour** — no login possible, which blocked half my test plan (see
   "Not tested"). Behind any NAT/CGNAT (office, campus, mobile carrier), one
   abusive user locks out every other user on that IP. Consider per-account
   buckets for login, or a higher IP cap.
3. **Open-redirect pattern on `next` params.** `/vote`, `/fb_react`, `/flag`
   do `redirect(data.get("next") or "/")` with no validation (app.py:939,
   2197). Templates only ever emit same-origin `next`, but a crafted POST can
   bounce a logged-in user to an arbitrary URL. (Memory notes this class was
   already reported; confirming it is still present.)
4. **Reaction widget: unknown.** A POST with `reaction=bogus_xyz` was accepted
   with a redirect; I could not verify whether the invalid value was stored or
   ignored (was logged out by then). Worth one check.

## Verified GOOD (no bug)

- **Stored XSS blocked everywhere:** `<script>` in post title, `<img onerror>`
  / `<svg onload>` / `javascript:` hrefs in post bodies and comment bodies are
  HTML-escaped on render — index, community, post page, and comment threads
  all show `&lt;script&gt;` etc. `link_mentions` escapes before linkifying.
- **Signup validation:** duplicate handle → 400 with friendly "handle taken —
  pick another"; mismatched passwords → 400.
- **Auth gating:** logged-out POSTs to /vote, /fb_react, /flag, /comment →
  401 / redirect-to-login as appropriate; /submit and /upload 302 → /login.
- **Error handling:** unknown post → 404, unknown path → 404 page, malformed
  JSON body → 400 `{"ok": False, ...}`, PUT/DELETE/GET on POST-only routes → 405.
- **Media pages all 200:** /shorts, /musefm, /musefm/shorts, /musefm/photos,
  /episodes, /episodes/ep01 (audio player → /audio/ep01.mp3 serves 200
  audio/mpeg), /guide, /signal, /network, /shop, /pet, /api/docs, /api/shorts
  (returns items JSON).
- **Double-vote semantics:** voting the same value twice does not double-count
  (score stayed 1); flipping 1 → -1 works.
