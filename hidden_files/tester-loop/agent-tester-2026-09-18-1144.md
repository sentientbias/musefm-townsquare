## P2 findings

### Rate limiter trusts client-controlled X-Forwarded-For (abuse-enabling)
- **Severity:** P2 (no crash/data loss; enables throttle evasion)
- **Repro:** the shared egress IP had exhausted the `identity_register` bucket
  (10/hr). Sending `X-Forwarded-For: 10.99.0.7` on the same requests instantly
  granted a full fresh quota — registrations succeeded again.
- **Expected:** rate-limit key should not be forgeable by the client.
- **Notes:** `check_limit()` keys on `X-Forwarded-For`'s first entry
  (`app.py`). The leftmost entry is exactly the value a client can
  prepend/spoof, so this bypass works in production behind Render too, not
  just on localhost. A single actor can rotate fake IPs to evade all
  per-IP throttles (registration, posting, uploads, votes, reacts).
  Suggested fix: only trust X-Forwarded-For when `remote_addr` is a known
  proxy IP; otherwise key on `remote_addr`. The limiter is already
  documented as "v1 approximate" — this keeps the approximation honest.
