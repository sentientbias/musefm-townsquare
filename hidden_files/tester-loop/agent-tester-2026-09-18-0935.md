## P1 (NEW — surfacing)

### 1. Shop idempotency-key retry returns 402 after balance drops (documented "Idempotent" contract broken)
- **Repro (exact):**
  - `POST /api/identity/register` `{"handle":"ag3_idem3","public_key":"<ed25519>"}` → 200
  - Two signed `{"action":"post",...}` → 200 each (identity earns 35 Signal: 2×10 posts + 15 "First Words" achievement)
  - `POST /api/shop/buy` signed `{"action":"shop_buy","item":"rename_token","idempotency_key":"key-DDD"}`
    → **200** `{"already_owned":false,"charged":20,"item":"rename_token","name":"Rename Token","ok":true,"pet":null,"spendable":15}`
  - Same request again (fresh signature, **same** `idempotency_key`, balance now 15 < 20)
    → **402** `{"error":"insufficient spendable Signal — Rename Token costs 20, you have 15 spendable","ok":false}`
- **Expected:** 200 with `{"already_owned":true,"charged":0,...}` — the idempotent no-op. The idempotency key exists precisely for client retries (e.g. after a timeout); the client is now told a completed, charged purchase "failed".
- **Root cause:** `shop.buy()` (`shop.py`) runs the `spendable < price` funds check BEFORE the `UNIQUE(fm_id, ref_id)` insert that implements idempotency. One-time items (accessory/bypass) check `owns()` first and retry correctly; consumables with an idempotency key do not. No double-charge occurs (the UNIQUE constraint would catch it), but the client-visible contract is wrong.
- **Proven by new test:** `test_shop_idem_retry.py` — 3 pass / 1 FAIL (`retry with same key is idempotent no-op` → `ValueError: insufficient spendable Signal`). Run: `.venv/bin/python test_shop_idem_retry.py`. Tests only; no source changed.
- **Suggested fix:** for consumables with an idempotency key, check for an existing `(fm_id, ref_id)` purchase row before the funds check (mirroring the `owns()` early-return for one-time items).

## P2 (NEW — logged)

### 2. `/api/upload/audio` performs no content validation (gif/video/image all magic-byte check)
- **Repro (exact):** `POST /api/upload/audio` multipart, signed `action="upload"` with `file_sha256=<sha256 of the bytes>`, `mime=audio/mp3`, file = 630 bytes of ASCII text (`b"plain text, not audio. " * 30`)
  → **200** `{"ok":true,"audio_url":"http://127.0.0.1:8473/audio/uploads/<id>",...}`
  → `GET <audio_url>` → **200**, `Content-Type: audio/mp3`, body = the text bytes.
- **Expected:** rejection like the sibling endpoints — gif requires GIF87a/89a magic (`gifs.is_gif_bytes`), video requires ftyp/EBML (`videos.detect_video`), image requires `ai_images.detect_image`. The audio path trusts only the client-declared (signed) `mime` string.
- **Impact:** arbitrary bytes stored and served from the app origin with an audio/* content-type. No direct XSS demonstrated (browsers won't render `audio/mpeg` as HTML on navigation), but it contradicts the documented safety model and, combined with the already-reported missing `X-Content-Type-Options` header, widens the sniffing surface. Inconsistency, not an active exploit.

## Observations (not findings)
- **Same Ed25519 pubkey registers under multiple handles** (R2/R2b/R2c → 200 each). No impersonation is possible — `fm_id` is bound inside every signature — and multi-handle sockpuppets are trivially achievable with multiple keypairs anyway. Not a hole; noting for the record.
- **Nonce is burned even when business logic fails after signature verification** (M4: post to `community="nope_community"` → 400; resend identical body → 401 replay). Correct anti-replay behavior; clients must re-sign after a 400. Documented here so nobody "discovers" it later.
- **`/api/photos/create` uses `expected_action="upload"`**, the same action name as `/api/upload/*`. A fresh signed upload body passes signature verification there (fails later on `image_url` validation). Nonce single-use prevents real cross-endpoint replay. Design smell only.
- **Post-level `image_ai`/`video_ai` are independent signed fields** from the upload record's `ai_generated`. A user can upload `ai_generated=true` media but post it with `video_ai=false`. Per the code's own policy ("mislabeled uploads are a moderation matter"), not a bug.
- **SH2 initial "FAIL" was my test's error, not the app's:** that identity had earned ~80 Signal from earlier test posts, so 200 was correct. True insufficient-funds (SH5, fresh identity) → 402 as designed. Spendable-balance math (`lifetime − spent`, lifetime never decreases) verified correct.
