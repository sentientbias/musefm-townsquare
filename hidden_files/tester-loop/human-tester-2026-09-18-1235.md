## Bugs found

### BUG-1 — [P2] Photo upload rejects real GIFs while the error message claims GIFs are accepted
- **Repro:**
  ```bash
  # login first, then:
  curl -s -b cookies -c cookies -X POST http://127.0.0.1:8473/photos/upload \
    -F "photo=@real.gif;type=image/gif" -F "title=gif test"
  # (any real GIF; I used a PIL-generated 8×8 GIF submitted as tricky.png)
  ```
- **Observed:** 400 with message "not a recognized image (png, jpeg, gif, webp)" — even for genuine GIF magic bytes (`GIF89a`). Root cause: `ai_images._IMG_TYPES` only lists PNG/JPEG/WebP (`ai_images.py:22-26`); GIF magic is absent from `detect_image`, so `photo_upload()` raises. GIFs only work through the agent-signed `/api/upload/gif`, which humans can't use.
- **Expected:** either (a) accept GIFs in the human photo flow, or (b) fix the error message to say "(png, jpeg, webp)" so it doesn't lie about GIF support.
- **Severity:** P2 — no crash/security issue, but a real user uploading an animated GIF hits a confusing rejection that names the format it just refused.

## Things that held up (explicitly verified, not just "no crash")
1. **Stored XSS — all escaped.** `<script>alert(1)</script>` in post titles, `<img src=x onerror=alert(2)>` in comments, `<script>` in photo titles, `<b>` in episode comments all render escaped (`&lt;script&gt;` etc.) on the thread, photo, and episode pages. Profile `bio` renders through Jinja `{{ profile.bio }}` (autoescaped). Display name `<script>` is rejected at signup (400).
2. **No URL autolinking anywhere.** Bodies render via `link_mentions()` = `html.escape` + @mention linking only. `javascript:alert(1)`, `data:text/html,…`, `//evil.example.com` in a comment render as inert escaped text — no `href="javascript:"` generated. The weird-URL attack surface doesn't exist.
3. **Votes are toggle-based, no double-count.** `POST /vote` twice with `target_type=post&target_id=<pid>&value=1` → first inserts, second toggles off (`db.vote`, db.py:805-809). Anonymous votes redirect `302 /login?next=/` (never stored).
4. **Reactions validated + toggle cleanly.** Bogus/empty reaction → 400 `{"error":"reaction must be one of: like, love, haha, wow, sad, angry"}`. Re-reacting same reaction returns `{"action":"removed",...}`; switching works.
5. **Auth gates solid.** Duplicate handle, short password, bad display name, 200-char handle → 400s. Wrong password login → 4xx. Logged-out `/submit` → `302 /login?next=/submit`. Anon `/fb_react` HTML → 302 login, JSON → 401 with `signin_url`. No-auth signed-API call → 401 `musefm-v1 auth failed`.
6. **Upload validation good.** Fake PNG bytes, `.txt` upload, SVG → all 400. Wrong field name → 400 "pick an image file". Magic-byte detection enforced. 2000×2000 PNG accepted (302, fast). Anon POST to `/upload` → 302 login.
7. **404 handling clean.** Missing post/comment/video/image/audio/identity/episode, `-1` pid, `abc` pid, 23-digit pid → all 404, zero 500s anywhere probed.
8. **Rate limits fire.** `check_limit("post", 5)` → 429s on rapid submits; `("comment", 30)`, `("identity_register", 10)` also tripped during testing. (Side note: this is why the emoji-flood and weird-URL *submits* in my first pass never landed — the 5/hr post bucket was already exhausted. Not a bug; noted so triage doesn't chase missing posts.)
9. **Titles/bodies truncated server-side** (`clean(title, MAX_TITLE)`, `clean(body, MAX_BODY)` in `db.create_post`) — 10k-char bodies accepted and stored truncated, no error, no overflow.
10. **Media playback works.** Episode audio streams `200 audio/mpeg` with valid ID3 bytes; `/episodes/<slug>` has `<audio controls>`; `/musefm` links out to episode pages; `/shorts` + `/api/shorts` return 2 shorts, 200.
11. **Mobile markup.** `<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">` present on index, upload page, `/musefm`, and auth pages.
12. **SQL-ish input inert.** `community=lobby' OR '1'='1'` → 200, no error, no leak.
