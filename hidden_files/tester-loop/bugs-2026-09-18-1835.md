## P1 (NEW — surface in chat)

### 1. Web audio upload trusts client-supplied Content-Type — PNG served as audio/mpeg
- **Found by:** Human tester (live repro). **Verified at source** (app.py:3696+,
  `f = request.files.get("audio")`; `mime = (f.mimetype or "").lower()` — no
  magic-byte sniffing). **Proven by new failing test**
  `test_upload_audio_mimetype_2026_09_18.py` (the PNG case fails today).
- **Repro:** POST `/upload` (logged-in human) with
  `files={"audio": ("notaudio.png", <67-byte PNG>, "audio/mpeg")}` → **302 accepted**;
  stored as `uploads/<n>.mp3`; served at `/audio/uploads/<n>` with `audio/mpeg`.
- **Contrast:** `/photos/upload` does real magic-byte detection; the signed
  `/api/upload/audio` requires `file_sha256` binding. Only the human web path is
  this lax.
- **Expected:** server-side content sniffing on the web path too (mirror
  `ai_images._IMG_TYPES`-style detection for audio: ID3/RIFF/Ogg/ftyp magic).
- **Related:** 09:35 noted "/api/upload/audio performs no content validation" (the
  API path) — this is a distinct, separately-fixable instance on the web path.

### 2. Missing CSRF tokens on session-authenticated write endpoints
- **Found by:** Human tester (code audit + session tests). **Verified at source:**
  `_check_csrf()` is wired into add_comment, episode_comment, pet_web_rename,
  flag_web, comment_edit, settings/*, video_comment_web — but NOT into
  `/submit` (create post!), web `/fb_react`, `/photos/upload`, `/upload`.
- **Repro:** log in, then POST `/submit` with title/body and no `csrf_token` →
  post is created.
- **Impact:** P1 defense-in-depth, not P0 — session cookie is `SameSite=Lax`, so
  cross-site POSTs don't carry it in modern browsers. Still: the four endpoints
  are precisely the highest-value write targets (post creation, uploads).
- **Expected:** `_check_csrf()` on all state-changing session endpoints, consistent
  with the other nine handlers.
