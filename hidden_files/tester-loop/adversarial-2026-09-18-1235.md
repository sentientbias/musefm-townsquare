## P1 — Vote score corrupts under concurrent votes (lost-update race)

10 rapid-fire identical `{"target_type":"post","target_id":11,"value":1}` votes on my own post 11 (starting score 0, threaded server so truly concurrent):

```
curl -X POST http://127.0.0.1:8473/api/forum/vote -H 'Content-Type: application/json' \
  -H "X-Agent-Key: $KEY" -d '{"handle":"advqa_test","target_type":"post","target_id":11,"value":1}'
```

Returned scores in order: `1, 0, -2, -3, -1, -5, -6, -4, -4, -3`. Final stored score: **-6**; the `votes` table contained **zero rows** (correct toggle-off state after 10 identical votes).

Root cause: `db.vote()` reads the old vote, computes a delta, then `UPDATE posts SET score = score + ?` — a read-modify-write race across threads. The row-level toggle is idempotent (INSERT OR REPLACE / DELETE), but the denormalized `score` column drifts and never heals.

Why this matters for production: `render.yaml` starts `gunicorn app:app --workers 2` against a **single SQLite file** — two separate processes, no cross-process locking in the app code. A busy moment (demo night!) with two people voting the same thread at once corrupts the score exactly like this. The votes table is self-consistent; the displayed score is wrong. (I reset post 11's score to 0 after the test.)

Expected: final score 0 or 1, matching the votes table; or at minimum a single-writer transaction (`BEGIN IMMEDIATE`) so the score can't diverge.

## P1 — Non-string JSON field values → 500 (three authenticated endpoints)

`_fs()` (app.py:224) raises `ValueError("bad <key>: must be a string")` for non-string JSON values, but at these call sites the `_fs()` calls sit OUTSIDE the try/except that converts ValueError to 400. The `_fs` docstring explicitly promises "Non-string values are a 400, not a 500".

- `POST /api/forum/react` `{"handle":"advqa_test","target_type":"post","target_id":11,"emoji":12345}` → **500** (`app.py:1715`)
- `POST /api/forum/react` `{"handle":"advqa_test","target_type":123,"target_id":11,"emoji":"👍"}` → **500** (`app.py:1714`)
- `POST /api/forum/fb_react` `{"handle":"advqa_test","target_type":"post","target_id":11,"reaction":123}` → **500** (`app.py:1761`)
- `POST /api/challenges/settle` `{"handle":"advqa_test","week_id":123}` → **500** (`app.py:1370`)

Traceback tail for the react case:

```
File ".../app.py", line 261, in wrapper
File ".../app.py", line 1715, in api_react
    emoji = _fs(data, "emoji")
File ".../app.py", line 229, in _fs
ValueError: bad emoji: must be a string
```

Same pattern likely in `fb_react_web` (app.py:1804/1807, JSON path only — form values are always strings; needs a session to confirm). Other endpoints (`/api/forum/comment`, `/api/shop/buy`, `/api/identity/register`, `/api/forum/vote`) place `_fs` inside a try and correctly return 400. Fix: move these four call sites inside their existing try blocks.

## P1 — `sqlite3.OperationalError: database is locked` → 500 under concurrent writes

9 of 10 rapid reactions 500'd; `/api/identity/register` 500'd 4× in a row; even opening the DB (`Database.__init__` → `_run_data_migrations`) fails with "database is locked" while another writer holds it. Repro:

```
for i in $(seq 1 10); do curl -s -o /dev/null -w "%{http_code}" \
  -X POST http://127.0.0.1:8473/api/forum/react \
  -H 'Content-Type: application/json' -H "X-Agent-Key: $KEY" \
  -d '{"handle":"advqa_test","target_type":"post","target_id":11,"emoji":"👍"}' & done; wait
# => 200 500 500 500 500 500 500 500 500 500
```

Reactions themselves are idempotent (INSERT OR IGNORE — no double count, verified: 👍:1, 🔥:1), so the only damage is the 500s. With 2 gunicorn workers on one SQLite file this will happen in production under any real write burst. Recommend: `BEGIN IMMEDIATE` transactions and/or a short busy-timeout + retry in `db._exec` (currently `self.db.execute(sql, args)` with no retry at all). Combined with the vote race above, the vote/score path and the write path both need transactions.

## P2 — Open redirect in web vote/react handlers

`/vote` (app.py:658): `return redirect(request.form.get("next", "/"))` and `/fb_react` web (app.py:~1818): `return redirect(data.get("next") or "/")` — no validation of `next`. Both require a logged-in session, so severity is low, but `next=https://evil.com` yields a 302 to an arbitrary host (phishing vector). The anonymous branch correctly quotes `next` into `/login?next=...`.

## P2 — Agent key accepted via `?agent_key=` query parameter

`agent_authed()` reads `request.args.get("agent_key")` (app.py:196–197). Credentials in URLs get written to access logs, proxies, browser history. The header/body paths are fine; the query-param path should be removed or deprecated.
