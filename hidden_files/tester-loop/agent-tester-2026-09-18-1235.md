## Environment artifacts discovered (not app bugs — read before triaging)

### A. The live server at 127.0.0.1:8473 was running STALE code
`videos.py` in the working tree was modified at 17:39:40 UTC — **15 seconds after** the test server process started (17:39:25 UTC). Python loads modules once at import, so the running server's in-memory `create_video_upload` did NOT include the uncommitted working-tree addition of `validate_video_structure()` / `MIN_VIDEO_BYTES` / `_mp4_has_moov` (see `git diff -- videos.py`).

Consequence: my first probe run **incorrectly "found"** that a 108-byte `ftyp`+zeros video was accepted (HTTP 200, `ok:true`, id 2). Re-running the exact same bytes against the **current checkout** (hermetic Flask TestClient, fresh DB) returns **400 `corrupt or truncated video file -- please re-upload`**. The checkout is correct; the live server was simply older. Repro of the false finding (against stale server):
- Multipart POST `/api/upload/video` with a valid musefm-v1 signature (`action=upload`, correct `file_sha256`), file = `struct.pack(">I",16) + b"ftyp" + b"\x00"*100` (108 bytes).
- Response: `200 {"ok":true,"id":3,"video_url":"/video/3","bytes":108,...}` — accepted.
- Same bytes through the checkout's `videos.validate_video_structure()` → `False` → `ValueError` → 400. **Not a bug.**

⚠️ **Process note for the tester loop:** the loop boots the server, then the working tree can change under it (uncommitted edits landed mid-run). Any "finding" from the live HTTP instance should be re-verified against the checkout before being filed, or the server should be rebooted after checkout changes.

### B. Rate-limit 429s contaminated the first probe run
The per-IP rate-limit buckets (`client_ip()` = REMOTE_ADDR) are shared by all three testers hammering the same localhost server. The human tester filled the `post` bucket before my first signed post even ran, so my initial "valid signed post rejected" (P0) and "valid signed comment/vote rejected" findings were 429/None-cascade artifacts, not auth bugs. Re-run with isolated REMOTE_ADDR: all accepted (post → 200 id, comment → 200, vote → 200, react → 200).

### C. `sqlite3.OperationalError: database is locked` 500s under concurrent load (P1, real mechanism)
While all three testers hit the one threaded server simultaneously, signed `/api/forum/react` requests intermittently returned **500 Internal Server Error** with this traceback (from `hidden_files/tester-loop/server.log`):
```
File ".../identity.py", line 196, in verify_signed_body
    if not db.note_nonce(nonce, NONCE_TTL_SEC):
File ".../db.py", line 1119, in note_nonce
    self._exec("DELETE FROM seen_nonces WHERE expires_at <= ?")
sqlite3.OperationalError: database is locked
```
The DB layer sets `PRAGMA busy_timeout = 5000` per connection, so a 500 means writer contention exceeded 5 seconds (rollback-journal mode: writers take an exclusive lock; three testers uploading/voting/reacting concurrently can starve each other). This is **not reproducible as an app-logic bug in isolation**, but the mechanism is real for production: under genuine concurrent agent traffic, legitimate signed writes can sporadically 500 — including at `note_nonce`, i.e. *after* signature verification (nonce is not burned, so a client retry is safe). Worth a hardening pass: WAL mode, or retry-with-backoff around nonce writes / upload INSERTs. **Severity: P1 (broken feature under concurrent load), with the caveat that the trigger here was three testers sharing one SQLite file.**

## Attestation check
The `ai_generated` self-declaration rides inside the signed body and the server's sha256-of-uploaded-bytes check binds it to the actual file (cases 22–23). The flag persisted to `video_uploads.ai_generated = 1` (case 39), and the served-image path works (case —). The provenance model described in the code comments ("the uploader's signature IS the provenance attestation") held up end to end. A tampered `ai_generated` value would break the signature (same mechanism as case 4).

## Notes / open questions (not filed as bugs)
- **Vote toggle:** repeated +1 votes toggle the vote off then on (scores observed: 1 → 0 → 1). Presumed intentional toggle semantics; flagging only because an agent client might expect idempotent upvotes.
- **Malformed JSON → 401** rather than 400 on signed endpoints: `require_agent_or_signature` treats unparseable JSON as "no auth presented". Defensible (auth-first), but a 400-vs-401 nit if API-docs strictness matters.
- **Nonce burn ordering is correct:** `verify_signed_body` burns the nonce only *after* signature verification, so invalid requests don't consume nonces — verified by code read and by case 4/5 (bad sigs → 401, and a fresh nonce still works afterward).
