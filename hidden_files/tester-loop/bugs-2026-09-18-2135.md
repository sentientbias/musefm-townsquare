## P1 (NEW — SURFACE LOUDLY in chat)

### 1. All write actions on detail pages broken — `{{ CSRF }}` undefined, every form 403s
- **Found by:** Human tester (empirical + code inspection). **Verified at source by triage.**
- `templates/post.html` (4 forms), `templates/episode_watch.html` (3 forms), and
  `templates/watch.html` (`{% set CSRF = CSRF if session_identity else "" %}` — self-referential, also empty)
  render `value="{{ CSRF }}"` / pass `CSRF` into the `vote_controls`/`flag_btn` macros in `_comments.html`.
- `app.py:531 inject_globals()` provides only **`csrf_token`** (the `_csrf_token` callable).
  The name `CSRF` exists nowhere in app.py — Jinja renders it as an empty string.
- **Repro:** log in, load a thread/video/episode page, submit any comment, reply, edit, flag,
  or vote → 403 "bad form token" (tester confirmed via clean curl: empty token → 403,
  valid token from the page meta tag → 302 success).
- **Proven by new failing test** `test_p1_csrf_human_handle_2026_09_18.py` (the empty-token
  check fails today: 4 of 4 rendered inputs empty).
- **Impact:** a human literally cannot comment on a thread, reply, flag, or vote from any
  detail page. Listing pages use `{{ csrf_token() }}` correctly, so only detail pages break.
- **Regression check:** the 18:35 run's human tester verified comments worked and vote toggles
  were correct — this breakage is NEW since `88d99cd`. Introduced with the "Comment surfaces,
  professionalized" template pass (`9a74b18`).
- **Expected:** `{{ csrf_token() }}` everywhere the templates say `{{ CSRF }}`.

### 2. SECURITY: any muse can self-assert `human_handle` — verified pairing flow bypassed
- **Found by:** Agent tester (code inspection + signed-flow probes). **Verified at source by triage.**
- `POST /api/identity/update` (signed, action `identity_update`) passes `human_handle` straight
  through: app.py:1602 → `db.update_identity(fm_id, ..., human_handle=...)`.
- `db.py:1443-1479 update_identity`: checks only format (`HUMAN_HANDLE_RE`) and requires
  `visibility == "linked"` first. No pairing code, no human-side consent, no lookup against
  `human_muse_links`.
- **Worse:** the *verified* `link_muse` flow (`consume_link_code`) writes only to
  `human_muse_links` + `link_audit` — it **never writes the `human_handle` column at all**.
  The only two writes to that column are both inside `update_identity` (db.py:1470-1479).
  So every public `human_handle` is self-asserted *by definition*; a muse can publicly
  claim "linked to human @Whoever" with zero involvement from that human.
- `db.public_profile` exposes `human_handle` whenever `visibility == "linked"` (db.py:1549) —
  the exposure gate the 18:35 run verified still holds, but the value it exposes is untrusted.
- **Repro (empirically confirmed end-to-end, not just code-read):** register identity →
  sign `identity_update` with `visibility=linked` → 200; then sign `identity_update` with
  `human_handle=SomeRealHuman` (format-valid, no pairing code, no human consent, no
  `human_muse_links` row) → **200**; `GET /api/identity/<fm_id>` public profile then
  exposes `human_handle: "SomeRealHuman"`. (Live-set test via the loop instance was blocked
  by rate-limit contention; reproduced hermetically via Flask test client.)
  **Proven by new failing test** `test_p1_csrf_human_handle_2026_09_18.py` (the two
  human_handle checks fail today).
- **Expected:** reject `human_handle` in `update_identity` unless a verified row exists in
- **Expected:** reject `human_handle` in `update_identity` unless a verified row exists in
  `human_muse_links` for that fm_id; better yet, remove `human_handle` from `update_identity`
  entirely and let only `link_muse`/`unlink` manage it.
- **Why this matters for the mission:** the human↔muse pairing flow is the airtight-trust
  centerpiece of the demo-night story ("verified human↔agent connections"). Self-assertable
  human linkage breaks that claim end to end.
